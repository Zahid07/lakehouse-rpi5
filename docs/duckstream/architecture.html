A realtime sensor lakehouse, entirely on DuckDB

Sensors to queryable marts in about two seconds, with no broker cluster, no JVM, and no second database. One unbuilt piece stands between today and this: the trigger.

The whole system

Everything below the dashed line is DuckDB. The landing tree is parquet on the same disk; the marts are DuckLake, which is DuckDB’s lakehouse format. There is no other process in the picture.

What changes: the trigger, and only the trigger

Cron cannot go below a minute. A daemon can go to seconds.

Today duckstream ships AvailableNow and Once — both mean “drain what is there, then exit”. That makes cron the driver, and cron’s floor is sixty seconds. That single fact is the whole distance between what exists and a realtime lakehouse.

The objection to a long-lived daemon was always the catalog lock: one process at a time, and a daemon would hold it forever. Measured on this Pi, that objection dissolves — DETACH releases the lock, so a daemon can cycle and still leave the catalog reachable.

The loop, in full

# the ProcessingTime trigger — the one unbuilt piece
engine = Engine(con, catalog="ducklake:catalog.ducklake", data_path="lake_data")

while running:
    engine.attach()                      # ~11 ms — warm process, extension already loaded
    engine.run(trigger=AvailableNow())   # the existing trigger, unchanged
    engine.detach()                      # releases the catalog lock  ← measured
    sleep(2.0)                           # everyone else can ATTACH in this window

Note what is not new here. AvailableNow already drains until the source is empty; the transaction boundary, the exactly-once commit, the tier routing and the state store are all untouched. What is missing is the surrounding loop and the discipline about when the lock is held.

Why the daemon is safer than it sounds

A second writer was never the hazard — DuckDB’s catalog lock makes that structurally impossible, which is what §2.5 was corrected to say in phase 2b. The hazard was a daemon holding the lock indefinitely and locking out the operator’s own tools. Releasing on every cycle removes it: measured on this Pi, a reader attached successfully 21 times out of 25 against a writer cycling attach and detach.

The one real limit, stated plainly

One process may hold the catalog at a time. That is DuckDB’s file lock on the .ducklake file — which is itself a DuckDB database — and it applies to attaching, not merely to writing: a second process cannot attach even READ_ONLY. Cycling DETACH makes this workable rather than removing it. The documented escape is a SQLite or PostgreSQL catalog, which §2.5 names for multiple local processes and which nobody here has measured yet.

Every figure on this page was measured on this Raspberry Pi 5 — aarch64, 4 cores, 4 GB, DuckDB 1.5.5, ducklake d8a1881e — on 26 August 2026.
