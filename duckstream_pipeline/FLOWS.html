How the pipeline works

Two processes, one landing tree, three models and a star schema. Every number on this page was measured on this machine.

The whole thing, end to end

Sensor to queryable table

Two processes that never talk to each other directly. They meet at the landing tree — ordinary parquet files on disk — and that meeting point is what makes the whole design work.

Why two processes and not one

They have different jobs and different uptime requirements

The sensor sends about a hundred readings a second. A DuckLake commit costs ~26 ms on this machine, so writing each reading straight to the database caps out around 35 a second — you would fall behind immediately and never recover. And every commit writes its own parquet file and catalog snapshot, so you would also produce millions of tiny files a day.

Ingest absorbs that: it holds readings in memory and writes them out in batches, turning 2,000 readings into one file instead of 2,000 writes.

The three models

Same data, three different problems

Each model reads the same landing files and produces a different table. What separates them is whether their maths can be folded — whether a new batch can be combined into an existing answer without re-reading what came before.

The mistake this prevents

Before duckstream, the FFT mart transformed only the rows in the current batch. A one-minute window fed by 30-second dumps produced a spectrum over half a window — 51 frequency bins where the truth was 201 — and it never raised an error. It was simply wrong. duckstream refuses to fold an FFT at load time, before a single row moves, which is why that mart now has to recompute the window.

What TOOK includes — and the two things it does not

The dashboard, and the bug that shaped it

A reader that starved the writer

The catalog admits one process at a time, so a dashboard reading it competes with the pipeline writing it. The obvious design — attach per request — lost that competition in the wrong direction.

Two numbers that were wrong

Both read reassuringly while measuring the wrong thing

ShowedWhy it was wrongNow
“Waiting in landing” Counted every chunk on disk. The pipeline never deletes a consumed chunk — a tier-three model reads them back to recompute a window — so it only ever grew. It measured uptime, not backlog. Chunks processed and Chunks remaining. A chunk counts as processed only when every model has taken it; reporting the fastest would show zero while a slower model was still behind.
Throughput total, 3× too high Summed rows_in across models, and every model reads every chunk. 139,928 readings displayed as 419,784 — disagreeing with the “Readings stored” tile by exactly the model count. The largest single model’s total, with the multiplier stated: “258,131 readings × 3 models”. Labelled “last 120 batches”, since it is a window and will read below the lifetime tile.

Both are the same failure in different clothes, and it is the one this project keeps naming: a display that reads reassuringly while not measuring what it says. The pipeline log had it too — it printed only models that committed, so a failed model vanished from the log rather than reporting.

How long it takes

database commit floor~26 mswhy per-reading writes are impossible, not merely slow

To go faster, lower --flush-seconds first — that is where most of the delay sits. Below a second or two there is nothing left to win: each commit costs ~26 ms and writes its own file and snapshot, so committing more often just means more overhead for less data each time.

Running it, and reading the log

.venv/bin/python -u -m duckstream_pipeline.ingest --flush-seconds 5 --flush-rows 2000 \

# terminal 2 — the pipeline
.venv/bin/python -u -m duckstream_pipeline.pipeline --interval "3 seconds" \

One rule

Run one ingest at a time. Two subscribers on the same topic both receive every message, so both would land it and every reading would be counted twice.
